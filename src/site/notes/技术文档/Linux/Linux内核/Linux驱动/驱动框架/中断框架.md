# 背景

## 中断类型
- **NVIC**(Nested Vector interrupt controller)
- **GIC**（Global interrupt controller）：是ARM架构下负责管理所有中断的核心硬件，它像一个总调度中心，负责接收、优先级排序和分发中断信号给CPU核心。
	- **中断类型**：GIC将中断源分为几种类型，在设备树中通过`interrupts`属性的第一个细胞（cell）来指定。
	    - **SPI (Shared Peripheral Interrupt)**：即**共享外设中断**，其类型值为`0`。这类中断不是特定属于某一个CPU核心的，而是可以被分发给任何一个CPU核心处理。大部分来自芯片外设（如ADC、UART、I2C等）的中断都属于SPI类型。
	    - **PPI (Private Peripheral Interrupt)**：即**私有外设中断**，类型值为`1`。这类中断是某个CPU核心私有的，只由该核心处理。


## 中断上下半部

**中断完整步骤**
```
一个完整的中断需要做的事：
├── 读取硬件状态寄存器      ← 快，☀️ 必须在中断里做
├── 清除中断标志            ← 快，☀️ 必须在中断里做
├── 获取数据               ← 快，☀️ 必须在中断里做
├── 去抖处理（等 20ms）    ← 慢，❌ 不能在中断里做
├── 上报按键事件           ← 慢，❌ 不能在中断里做（可能唤醒进程）
└── 唤醒等待的进程          ← 慢，❌ 不能在中断里做
```

**中断下半部机制**

|机制|上下文|能否 sleep|特点|
|---|---|---|---|
|**软中断（softirq）**|软中断上下文|❌|最快，但编程复杂，只有少数子系统用（网络、块设备）|
|**tasklet**|软中断上下文|❌|基于软中断，简单易用，同一 tasklet 不会被并行执行|
|**工作队列（workqueue）**|进程上下文|✅|最灵活，可以 sleep，gpio-keys 用的就是它|
## 中断上下文
在中断处理程序里运行时，就是中断上下文。

**与其他上下文的对比**

|机制|API|上下文|能否 sleep|适用场景|
|---|---|---|---|---|
|**硬中断 ISR**|`request_irq`|中断上下文|❌|必须极快处理的事|
|**线程化中断**|`request_threaded_irq`|进程上下文|✅|可以慢慢干，替代 workqueue|
|**tasklet**|`tasklet_schedule`|软中断|❌|较轻的快速处理|
|**工作队列**|`schedule_work` / `mod_delayed_work`|进程上下文|✅|允许 sleep 的事|

# 上层API
## 绑定中断服务程序相关
- `devm_request_any_context_irq()`: 根据`irq_desc`内核自动判断应该跑在哪个上下文, 然后实际底层根据判断结果执行的`request_irq()/request_threaded_irq()`
- `request_irq()`: 硬中断, 跑在中断上下文
- `request_threaded_irq()`: 中断线程化, 跑在进程上下文
